**Date**: 2026-07-26  
**Status**: 採用済み（リファクタリング完了後着手予定）

## 背景

既存の「女性がキャリアとライフイベントを可視化するタイムラインアプリ」のリファクタリング完了後、プロダクトを大きくピボットし、社会課題解決およびユーザー体験の根本的な向上を図る。

1. **タイムライン構築の体験刷新**:
   既存の「手動でイベントをポチポチ配置する」UXは、これからライフプランを描くユーザーにとって思考のハードルが高い。AIエージェントとの対話を通じて、タイムラインが自律的かつインタラクティブに作成・更新・引き直しされるUX（Living Plan）への移行が求められている。
2. **社会課題解決とハッカソンアプライ**:
   [都知事杯オープンデータ・ハッカソン](https://odhackathon.metro.tokyo.lg.jp/) への参加を見据え、東京都および国のオープンデータを活用して「女性のキャリア形成とライフイベント（妊娠・出産・育休・復職）の両立」を強力に支援する社会課題解決型のプロダクトへ進化させる。

## 決定事項

コア体験のシンプルさとプロダクト価値の先鋭化のため、**「対話型AI × 女性キャリア統計オープンデータ」に100%フォーカス**してピボットを行う。

### 1. 対話型AIエージェント主導のタイムラインUX (Split-View)
- 左側に **AI Coach チャットパネル**、右側に **Live Timeline** を配置する Split-View UI を採用。
- ユーザーが「2年後に子どもがほしい」「育休明けは時短で復職したい」と対話すると、AIが Function Calling を介してタイムライン上に該当イベント群を自動でマウント・連動移動させる。
- ビジョン「*Compass, not a Mirror*（比較ではなく自分軸の参考値）」「*Empowerment, not Direction*（決定権は常にユーザー）」をAIのプロンプト・ペルソナに厳格に組み込む。

### 2. オープンデータ活用のフォーカス（文脈①：キャリア・ライフプランの標準モデル・参考軸）
- **目的**: 何も参考がないと描きにくいユーザーに対し、世の中の平均や選択肢のモデルを「押し付けではない参考（コンパス）」として対話内で提示する。
  → **一部 Superseded by [PDR-007](PDR-007-hide-averages-show-institutional-limits.md)**: 「平均をタイムライン上の参考値バンドとして提示する」という当初案は、平均という軸自体が他者比較と同じ焦りを生むため撤回した。平均は内部利用（テンプレート初期値の根拠）にとどめ、画面には制度上の上限値（B1: 出来事起点の相対的な上限）のみ出典付きで提示する方針に変更した。
- **採用データセット4選**:
  1. **東京都『次世代育成支援東京都行動計画』** (`t000054d0000000184`): 東京都の第一子平均出産年齢（約30.8歳）や出産間隔データ。
  2. **東京都『東京の男女平等参画データ』** (`t313360d0000000053`): 年代別女性就労形態推移、都内企業の役職別女性管理職割合。
  3. **厚生労働省『雇用均等基本調査』(e-Stat)**: 育休取得率（85%+）、育休期間分布（1年未満/1〜1.5年/2年）、復職率。
  4. **国立社会保障・人口問題研究所『出生動向基本調査』(e-Stat)**: 出産前後の就業継続/転職/離職パターン。

### 3. 開発時のデータ抽出・ローカルマスタ組込みワークフロー
- アプリ実行時に外部APIへ動的通信する複雑な設計（エラー対応・API変更依存リスク・通信遅延）は避け、**開発工程においてコーディングエージェント（AI）がオープンデータを収集・抽出してアプリ内に静的マスタ（JSON）として組込む**。
- **格納ファイル**:
  - `lib/features/open_data/data/career_stats_master.json`（統計・参考値マスタ）

## 検討経緯・スコープ調整（重要）

### 制度・手続・マネー機能（観点②）を初期スコープから外し「将来構想」とした経緯

当初、給付金や行政の支援制度（育休手当、児童手当、都の支援事業等）をタイムラインと連動させる構想を検討したが、議論・検討の結果、**初期スコープから外し、将来的な構想に留める判断を行った。**

#### 【判断の理由】
1. **プロダクトビジョン（`PRODUCT_VISION.md`）との整合性**:
   - ビジョンにおいて「財務シミュレーション（計算の正確性に責任を持てない）」は元々意図的なスコープ外と定められている。
   - 給付額の厳密な計算や複雑な制度要件に踏み込みすぎると、アプリが「行政手続きガイド」や「計算ツール」化してしまい、「自分らしい人生の軸（Well-being）を描くコンパス」という本来のCore価値が希薄化する。
2. **UXの入力摩擦の防止**:
   - 制度適用には「居住区市町村」「年収・世帯所得」「社会保険の種類」などプライベートで詳細な事前入力を強いることになり、ユーザーが軽やかにライフプランを描き始める体験を害する。
3. **ハッカソン・MVPでのメッセージの鋭角化**:
   - 「AIと対話し、都の女性キャリアデータを参考に自分だけのタイムラインを引き直す体験」にフォーカスを絞る方が、プロダクトの核がシンプルかつ圧倒的に力強く伝わる。

---

## 検討したが採らなかった案

1. **行政支援制度・給付金シミュレーション機能（観点②）の初期実装**
   - **採らなかった理由**: 上記の通り、入力摩擦・制度ルールの複雑さ・計算精度の責任問題があり、ライフプランを描く本質体験を邪魔するリスクがあるため。
2. **アプリ実行時におけるデータポータルAPIとのリアルタイム動的通信（動的RAG/MCP）**
   - **採らなかった理由**: ユーザー利用時の通信エラー・ネットワーク依存・データ仕様変更リスクが高く、アプリの動作遅延の原因となるため。開発時にオープンデータを抽出し、精査されたローカルマスタJSONとして保持する方が遥かに高精度・高速・堅牢であると判断した。
3. **他ユーザーのライフプランとの比較・SNS機能**
   - **採らなかった理由**: `PRODUCT_VISION` の Value 1（"Compass, not a Mirror"）に直接違反するため。他者と比較して焦るのではなく、自分の Well-being に向き合う体験を最優先する。

## 実行ロードマップ

- **Phase 0 (現在)**: リファクタリング作業の完了
- **Phase 1 (リファクタ直後)**: コーディングエージェント（AI）によるキャリア統計オープンデータ4選の抽出スクリプト実行、`career_stats_master.json` の作成・配置
  → **Superseded by [PDR-007](PDR-007-hide-averages-show-institutional-limits.md)**: `career_stats_master.json`（平均値を含む実行時マスタ）は作らない。採用データセットも見直し、平均値を含む文脈は内部専用の定数に、制度上限値は別データセット（子育て支援制度レジストリ `t000029d0000000034`）から抽出する構成に変更した。詳細は PDR-007 を参照。
- **Phase 2**: `ai_agent` feature の作成 (Split-View UI + Gemini API Function Calling によるタイムライン自動マウント)
- **Phase 3**: オープンデータ（キャリア参考値）と対話AIの連動ロジック実装・テスト
- **Phase 4**: 都知事杯オープンデータ・ハッカソン提出、プレゼン資料・動画作成、UIデザイン磨き込み
- **Future Expansion (将来構想)**: ライフプランが固まった後のステップとして、希望者向けの行政制度・マネー連携の検討

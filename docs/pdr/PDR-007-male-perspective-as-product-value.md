# PDR-007: 男性ユーザーによる気づきをプロダクト価値として記録する

**Date**: 2026-08-22
**Status**: 検討中（実現形は未決。ハッカソン提出後に判断）
**Owner**: プロダクトオーナー / AI Coding Agent

---

## 背景

プロダクトオーナー（妻）から次の意見が出た。

> このアプリを男性が使うことで、女性のキャリアがいかに大変なのかわかる、みたいなのも良いかもね。

現状のプロダクトは `PRODUCT_VISION.md` の時点で女性個人が自分のプランを描くツールとして定義されている（Vision:「すべての女性が…」、Primary ターゲット:「20〜40代の女性」）。パートナー・配偶者・共有は VISION / PRD / SPEC / PDR / ADR のどこにも要件として存在せず、明示的なスコープ外宣言すらされていない未検討領域である。

一方で、この意見が指す体験（産休・育休が働き盛りの時期に重なることで生じるキャリアの断絶を、男性が可視化を通じて理解する）は、既存の資産と強く接続する。

- `PRD.md` Phase 4（スコープ外）に **F-11「キャリアブランク影響の可視化」** が棚上げされたまま残っている
- ハッカソン提出物の利用予定オープンデータに既に「東京の男女平等参画データ2017」が入っている（PDR-006）
- 規定カタログには同棲開始・結婚意思共有・プロポーズ・両家顔合わせなど、本質的に2人が関与するイベントが11件含まれるのに、データモデル（`LifeEvent` / `UserProfile`）は単独ユーザー前提である

この PDR は、この意見をプロダクトの検討対象となる価値として記録し、既存の Issue / PRD 項目をこの文脈に紐付け直すことを目的とする。**この PDR の時点では実装は行わない。**

---

## 決定事項

1. 「男性が使うことで女性のキャリアの現実に気づく」を、プロダクトが今後検討しうる価値として認識する。
2. 都知事杯オープンデータ・ハッカソン提出（2026-08-23 締切）のスコープには含めない。提出原稿・プレゼン骨子は変更しない。
3. 実現形（後述の案A/B/C）は決めない。判断は後日、Issue で管理する。
4. `PRODUCT_VISION.md` の Value 3（First-class Citizen）との整合の考え方を、この PDR で確定した整理として記録する（下記「Value 3 との関係」）。
5. Value 1（Compass, not a Mirror）が禁じた「他者との比較」との違いを、この PDR で切り分けて記録する（下記「Value 1 との関係」）。

`PRODUCT_VISION.md` のターゲット定義・Vision 文はこの PDR の時点では書き換えない。書き換えは実現形が決まってから判断する。

---

## Value 3 との関係

`PRODUCT_VISION.md` の Value 3（First-class Citizen）は次のように定める。

> 産休・育休・妊活などのライフイベントは、例外やブランクではなく、人生の中心的な概念として扱う。
> 「ブランク」「空白期間」「キャリアの遅れ」を示すラベルや表現を使わない。これらのカテゴリは仕事イベントと同一のタイムライン上に自然に存在する。

「断絶を見せる」というアイデアは、一見この禁止事項と正面衝突するように見える。しかし、後述の**案A（パートナーレーン併置）** の形を採る場合は衝突しない。同一時間軸に「自分」と「パートナー」の2人分を並べたとき、埋まっているのは女性側（産休・育休は first-class なイベントとして通常のイベントと同じ重みでそこにある）であり、空いているのは男性側になる。アプリ側は何も「ブランク」とは呼ばず、ラベリングも行わない。2人分の事実を同じ時間軸に並べるだけで、見る人が自分の側の空白に気づく。

これはむしろ Value 3 の「仕事イベントと同一のタイムライン上に自然に存在する」という記述の延長にある。産休・育休を特別視せず、対等な粒度で置くからこそ、隣に並べたときに空白が浮かび上がる。

この整理は、案A を検討する際に「Value 3 に反するのでは」という論点を再度立てないためにここに確定させておく。案B・案C はそもそも産休・育休の表現自体を変えないため、この論点は生じない。

---

## Value 1 との関係

Value 1（Compass, not a Mirror）および PDR-006 が却下した「他ユーザーのライフプランとの比較・SNS機能」は、**不特定他者との比較による焦り**を禁じたものである（「みんなの計画」的機能、ランキング、平均への同調圧力）。

パートナーとの併置は、不特定多数との比較ではなく、**同一世帯の当事者間での事実の共有**であり、性質が異なる。ただし「当事者として迎える」場合（後述）、男性側のプランにも Value 1 が同様に適用される点は変わらない。この PDR では、パートナー併置を Value 1 の禁止対象には含めない、という整理にとどめ、実装時の具体的な線引きは実現形が決まった時点で改めて検討する。

---

## 検討事項（決めていないこと）

### ターゲット拡大の是非

男性を利用者として迎える場合、位置づけには少なくとも2通りある。

- **観察者として**: 女性ユーザーのプランを見る側。VISION の Primary ターゲットは変えなくてよい。
- **当事者として**: 男性も自分のプランを描く。VISION / PRD のターゲット定義の書き換えが要る。この論点は既存の Issue #64「初回登録時の性別選択とテンプレート分岐（スコープ拡大の判断）」そのものである。

### 実現形の選択肢

| 案 | 内容 | 主なコスト |
|---|---|---|
| A. パートナーレーン併置 | 同一時間軸に「自分」「パートナー」を並べる | `LifeEvent` に owner 軸が必要。タイムラインのレーン構造が現状 bool 2値（仕事/プライベート）で組まれており、一般化が要る |
| B. オープンデータでの対比表示 | 男性育休取得率などを参考情報として重ねる | データモデル変更不要。ただし「自分ごと」としての気づきは案Aより弱い |
| C. 男性視点モード | 男性が自分のプランを作ると、対応する女性側に何が起きるかが見えるガイド的な体験 | 単独ユーザーモデルのまま可能。Value 1 との線引きの検討が必要 |

いずれを採るか、複数を組み合わせるかはこの PDR では決めない。

### 案Aを採る場合の技術的制約（事実として記録）

現状のタイムラインは「軸（仕事/プライベート）× 1人」の2レーン構造が bool 型でモデルから UI まで貫通している。

- `lib/features/timeline/domain/life_event.dart` — 所有者/人物を示すフィールドが無い。レーン判定は `isWork` getter（`catalogId` のハードコード集合）
- `lib/features/timeline/presentation/widgets/timeline_view.dart` — 行数が固定（`axisHeight + _rowHeight * 2`）、Y座標・タップ判定も `isWork` の三項演算子で二分岐
- `lib/features/timeline/presentation/widgets/timeline_lane_labels.dart` — 「仕事」「プライベート」をベタ書き
- `lib/features/timeline/domain/event_stacking.dart` — `for (final isWork in [true, false])` と `workMax / privateMax` の bool 前提
- `lib/features/timeline/presentation/widgets/dependency_connector.dart` — `Map<String, bool>` の eventLanes 前提
- データ層は `userId` family provider で「1ユーザー = 1タイムライン」。パートナー分のイベントを同一ユーザー配下に owner タグ付きで持つか、別ユーザーを参照する形にするかの設計判断も要る

`docs/adr/025-*.md` で座標系を「区間（面）」モデルに統一済みであり、レーン数の一般化はその延長線上にある。

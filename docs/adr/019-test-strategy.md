# ADR-019: テスト方針の再整備

**Date**: 2026-07-26
**Status**: 採用済み

## 背景

全体リファクタリングにあたり、テストを再整備する必要が出た。ただし方針なしに追加すると
テストが乱立するため、まず「何を書き、何を書かないか」を決めることにした。

前回のテスト方針 `TESTING_POLICY.md`（v2.0）は ADR-014 で `docs/archive/` に退避されている。
同じ失敗を繰り返さないため、実態と突き合わせて原因を分解した。

| 前回の記述 | 実態 | 原因 |
|---|---|---|
| `Owner: QA Agent` | ADR-014 で当該エージェント定義ごと廃止 | 持ち主を「役割」に紐づけた。役割が消えて無主になった |
| `Last Updated: 2025-XX-XX` | プレースホルダのまま埋まっていない | 初日から更新されていない。更新前提の文書は更新されない |
| 比率目安 ユニット70% / ウィジェット25% / 統合5% | 実測はほぼ達成していた | **数を数える基準は中身を問わない。** 比率を満たしたまま無価値なテストが積み上がった |
| 統合テスト `integration_test/` | 一度も作られていない。依存も無い | やらないことが「やる」と書かれ、長期間放置された |
| Logic層カバレッジ 80%以上 | 一度も計測されていない | 計測手段が無い数値目標は飾りになる |
| `save(event)` / `getAll()` / `delete(id)` のパターン列挙 | 実 API は `saveEvent` / `fetchEvents` / `deleteEvent` | 本番 API を書き写したため、コード変更で嘘になった |
| 「MVP時は」「Phase 3では」 | Phase は過ぎ、Firestore 実装は既にある | 時点依存の記述が凍結した |

**最大の欠陥は「何を書くか」しか書かれておらず「何を書かないか」が無かったこと。**
パターンのカタログとして機能したため、機械的に真似すれば増える一方だった。
実際 `predefined_life_event_test.dart` の18ケースは、前回方針の「Data層: `Map` と `DomainModel` の
相互変換」「const 生成」パターンをなぞった結果、`const` で生成して書いた値を読み返すだけの
内容になっていた。

## 決定

1. **判断基準を「落ちたとき何が壊れているか一言で言えるか」に置く。** 比率目標は設けない。
2. **層ごとに担保する範囲を分ける。** 純ロジック（`domain` / `logic`）で網羅し、
   ウィジェットテストは配線のみ各経路1本に留める。重心は純ロジック層。
3. **D&D は責務を分割する。** 座標→日付の変換・スナップ・境界は純粋関数のユニットテストで
   網羅し、ウィジェットテストは「ジェスチャが `DragTarget` に届き結果が Provider に渡る」
   ことだけを見る。ウィジェット層で網羅しようとすると必ず壊れやすくなるため。
4. **「書かないもの」を方針の中核に置く。** 単純 getter、見た目の値、フレームワーク自体の挙動、
   具象クラス名への依存、画面座標のハードコード。
5. **構造ルールはドキュメントではなくテストで守る。** `catalog_consistency_test.dart` が
   カタログの不変条件に対して既に果たしている役割の構造版として、
   `domain/` `logic/` の 1 lib : 1 test を検証するテストを置く。
6. **カバレッジのグローバル閾値は置かない。** 閾値は `domain/` と `logic/` のみに掛ける。
7. **独立した `TESTING_POLICY.md` を復活させない。** 判断と理由は日付固定の ADR（本文書）、
   日々参照する運用ルールは `CLAUDE.md` §5、構造ルールは CI が回すテストに置く。

## 理由

- 前回の失敗は内容以前に「単独で維持し続ける前提の文書だった」ことにある。維持義務が発生する
  場所を作らなければ、実態と乖離しようがない。ADR は日付固定の記録であり、覆すときは
  `Superseded by` を追記する（CLAUDE.md §6 の既存ルール）ため、更新漏れという概念が無い。
- グローバルなカバレッジ閾値は、`presentation/` の存在確認だけのテストを量産する圧力になる。
  実際、既存のウィジェットテストの大半が `find.text` / `find.byType` の存在確認に留まっていた。
  純粋関数に閾値を絞れば、高い数値に意味が伴う。
- 本番 API 名・件数・行番号を方針に書かないのは、ADR-014 §4 で決めた
  「変動する情報は単一情報源へのポインタだけを書く」の適用にあたる。

## 影響範囲

- `CLAUDE.md` §5（テスト方針を全面書き換え）
- `test/support/`（新設。モック定義・ビルダー・`pumpApp` を集約）
- `lib/features/timeline/presentation/timeline_keys.dart`（新設。テストが参照する Key の集約先）
- 既存テストの書き換え（具象クラス名依存と座標ハードコードの除去）
- `docs/archive/README.md`（`TESTING_POLICY.md` の行に本 ADR への導線を追記）

## 結果

**得るもの**

- 増やす基準と減らす基準の両方が揃う。テストの乱立を構造的に抑えられる。
- リファクタリングでテストが道連れにならない。実装差し替えで assertion が大量に書き換わるなら、
  それはテストが実装詳細に密着しすぎているサインだと判断できる。
- 方針の維持コストがゼロになる。

**失うもの**

- テストパターンの「写経元」が無くなる。前回方針にあった具体的なテスト例の一覧は、
  実際のテストコードを読んで真似する形になる。判断基準を持つ代わりに、
  書き方のテンプレートは提供しない。

## Follow-up（別タスク）

本 ADR は方針のみを扱った。以下はリファクタリングの各段階で実施する。

1. **既存テストの棚卸し** — 全26ファイルを本方針に照らして 維持 / 縮小 / 削除 に分類する。
   `predefined_life_event_test.dart` は削除候補。 → #40
2. **構造テストの追加** — `domain/` `logic/` の 1 lib : 1 test を検証する。 → #41
3. **カバレッジ計測の CI 追加** — 現状値を計測してから `domain/` `logic/` の閾値を確定する。 → #42
4. **未テスト feature の解消** — `auth` / `user_profile` / `core`。 → #43

以降の残課題は本節を追記せず GitHub Issue で管理する（CLAUDE.md §6）。

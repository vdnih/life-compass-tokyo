## なぜ

提出フォームが公開された（`都知事杯オープンデータ・ハッカソン2026 作品提出フォーム`）。**締切は 2026-08-23（日）17:00 JST、期限後は提出も修正も不可**。作成時点で 08-21、実質 2 日弱。

PDR-006 はこのハッカソンを見据えて 2026-07-26 に採用済みだが、作成時点でコードは Phase 0（リファクタリング）のままで、`lib/features/` に `open_data` も `ai_agent` も存在せず、`career_stats_master.json` も無い。`pubspec.yaml` に `http` / `firebase_ai` は無く、実行時に読む外部データ資産もない（assets は launcher icon のみ）。

→ 方針：**PDR-006 Phase 1〜2 を圧縮実行し、AI 対話まで 8/23 に間に合わせる。**

## 必要な機能実装（PDR-006 Phase 1〜2 の圧縮）

### Step 0：土台を固める（最初にやる）

- PR #77（ブロックベース座標系）をマージ
- PR #74（ゲストでも書き込み可）をレビュー→マージ — 審査員がログインせずに触れることは審査軸5に直結する最重要施策
- Firebase AI Logic の利用可否確認（Blaze プラン、API 有効化、`firebase_ai` の Web 対応）— ここが塞がっていると Phase 2 が丸ごと落ちるので最初に潰す

### Phase 1：オープンデータのローカルマスタ化（PDR-006 Phase 1 → PDR-007 で内容を差し替え）

新規 `lib/features/open_data/`（`catalog` と同様、`timeline` と並列に置く）。**PDR-007 の分類（A: 内部利用の中心値／B1: 出典付きで可視化する制度上限）に沿って2系統に分ける。**

- **B1（可視化する）**: `data/institutional_limits.dart` — 東京デジタル2030ビジョン（こどもDX）子育て支援制度レジストリ (`t000029d0000000034`、CC BY) から、対象年齢の上限が構造化されている制度（育休・産後ケア事業・児童手当・018サポート等）を抽出。育休の上限（子が2歳になるまで）は同レジストリに構造化データが無いため、育児・介護休業法を出典に手書きで持つ
- **A（内部利用のみ、UI に出さない）**: `data/reference_baselines.dart` — 出産テンプレート・カタログの初期値（育休12ヶ月など）の根拠を dartdoc の出典コメントとして残す。ファイル冒頭に「`presentation/` から参照禁止」を明記
- 各エントリに `source`（データセット名・提供元・URL・取得日）と `license` を必ず持たせる。これが 4-1 の原稿と、アプリ内の出典表示（B1 のみ）と、同意項目7のライセンス確認をまとめて成立させる
- `domain/institutional_limit.dart` — B1 の値オブジェクト（`catalogId` + 上限月数 + 事実文 + 出典）
- 実行時 I/O は増やさない。レジストリ本体（約90MB）はビルドに含めず、開発時に必要な数十件だけを Dart 定数へ抽出する
- 表現の制約：`PRODUCT_VISION.md` Value 1（PDR-007 で更新）「平均・中央値は内部利用にとどめ UI に出さない」、Value 4「〜すべき」「〜が必要」「リミット」を使わない。金額は出さない（財務シミュレーションのスコープ外に抵触するため）。文言レビューを実装の一部として扱う

Issue #63（「自然妊娠期間（35歳まで）」を参考値候補に）は、暦年齢に紐づく上限（PDR-007 の B2）に該当し焦りを生むため、引き続き入れない。

### Phase 1.5：制度上限を情報として見せる（最小UI）

- 既存の制約チェック（`constraint_checker_provider.dart`）の経路に B1 を合流させ、`ConstraintSeverity.info`（青・`info_outline`）として表示する。**タイムライン上に平均バンドを重ねる実装は行わない**（PDR-006 の当初案から撤回）
- 発火条件は「置かれた期間が制度上限未満のとき」のみ。ブロックはしない（Value 4）
- タップ／カードで出典（データセット名 + リンク）を表示
- `timeline_view.dart` は既に1000行超。ADR-021 の方針どおりレイヤーは別ウィジェットとして追加し、この PR で分割はしない
- テスト：上限判定は純関数側で網羅、ウィジェットは「出典付き情報カードが表示される」配線1本のみ（CLAUDE.md §5）

### Phase 2：AI 対話（PDR-006 Phase 2〜3）

- `pubspec.yaml` に `firebase_ai` を追加
- 新規 `lib/features/ai_agent/`
- UI は PR #72（draft spike）をそのまま土台にする。「モバイルはボトムシート、デスクトップは左パネルのタブ」「即時反映＋スナックバー Undo」という結論が既に出ており、`presentation/` 層のみの変更で `applyTemplate` / `deleteEvent` / `removeDependency` を呼ぶ構造になっている。固定応答部分を Gemini + Function Calling に差し替えるのが最短経路
- Function Calling で公開する関数は最小限に絞る：
  - `applyGoalTemplate(templateId, goalYearMonth)` → 既存 `goalTemplateProvider.applyTemplate()`
  - `addEventFromCatalog(catalogId, yearMonth)` → 既存 `timelineEventsProvider.addEventFromCatalog()`
  - `moveEvent(eventId, yearMonth)` → 既存 `move()`（依存の連動移動は `cascade_move_provider.dart` が既に担う）
  - `getInstitutionalLimit(catalogId)` → Phase 1 の B1 マスタのみを参照させる（A は関数として公開しない。AI が平均値を発話しないようにする設計上のガード）
- システムプロンプトに Value 1 / Value 4 を明示的に埋め込む（比較しない、平均を出さない、指示しない、決めるのはユーザー）
- ADR を新規に書く：`firebase_ai` 導入と、ADR-024 が予告していた「AI 呼び出しだけエミュレータを迂回して本番に到達する」制約の受け入れ

### 8/26 収録までに回せる範囲（8/23 に間に合わなくてよいもの）

デモ操作動画（3-8）、UI 磨き込み、`docs/PRD.md` v7.0 更新（Issue #60）、テスト補強。
